# Portal 文案规范

这份规范适用于 `apps/portal` 的玩家页面、登录、挑战提交、提交状态、空状态和管理后台。

目标很简单：让每句话都承担清楚的功能。优先使用短标签、直接标题和事实状态；只有能帮助用户完成当前操作时，才保留说明文字。

新增或修改任何 Portal 文案前，必须先查阅[Portal 术语表](terminology.md)。
版本更新（Changelog）的结构、排版与去 AI 化文案规范见[版本更新规范](changelog-guidelines.md)。
称号名称、称号槽位、展示方式和流程术语必须复用术语表中的写法；接口键和
数据库枚举值保持原样。

## 基本规则

- 用短语和名词短语描述页面内容：`暂无记录`、`未开放`、`提交记录`、`上传截图`。
- 用事实描述状态，不替用户解释整条流程：`读取中…`、`提交中…`、`识别中…`、`已收到`。
- 标题说明“是什么”，说明文字只补充必要的条件、范围或限制。
- 空状态默认只显示当前状态。只有存在明确、可执行的下一步时，才增加按钮或引导。
- 错误指出具体对象和下一步：`无法读取挑战目录，请稍后重试。`
- 未来功能使用 `未开放` 等事实标签，不写发布日期、承诺或“以后会在这里显示”。
- 面向玩家少用内部流程词汇，例如审核、发放、编排、持久化和 OCR；只有用户需要理解时才出现。
- 保持中文标点和现有 Portal 的系统字体、短标题、克制语气一致。

## 避免的句式

以下句式通常只是重复页面已经表达的信息，应优先删除或改成短语：

- `这里……会……`
- `开放后会在这里显示`
- `留下每一次……`
- `正在……你的……`
- `完成后会自动……`
- `现在……已经整合，在这里……`
- `暂时无法……，请确认……，然后……`

不要为了“完整”补一段没有下一步的说明。页面已经有标题、状态或按钮时，不再用段落复述它们。

## 默认不添加解释性 UI

界面通过层级、布局、标签、数据、状态和操作自解释；支持性文字只在无法从
界面本身推断出信息时保留。默认信息层级：

**对象/字段 → 值/数据 → 真实状态 → 操作 → 分区标题 → 支持性文字**

支持性文字不得成为理解布局的主要手段。以下各解释性元素均为默认规则而非
绝对禁止；无障碍文本和隐藏语义标签始终有效，即使可见解释文字被移除。

- 页面 eyebrow/kicker：默认不加。
- 页面描述/副标题：默认不加；仅当范围、约束或必需下一步不明显时保留。
- 卡片 kicker：默认不加。
- 卡片/分区描述：仅当标题和可见内容无法传达重要业务区分时保留。
- 辅助文字：仅用于格式要求、约束、后果、风险或继续所需的信息。
- 徽标/状态：附着在它描述的对象上；不在单独的“状态”区域重复同一状态。
- `UAlert`：仅用于异常状态、风险、失败或需要操作的信息；不作常规描述性文字。
- Tooltip/popover 帮助：用于低频澄清，不用于弥补弱标签或弱布局。

### 删除测试与重复事实检查

保留一句可见的支持性文字前，先问：

> 删掉这句话后，目标用户是否仍能正确识别内容/状态并完成当前任务？

能，就删掉。第二重检查拒绝重复事实：一个事实通常只有一个主要可见表达。
`QQ 已绑定`、`未开放`、提交状态或页面目的在多个层级重复出现，必须有具体
理由。

### 有用与冗余的说明

有用（约束或后果无法从界面本身推断，用户需要它来行动）：

- `唯一 Key` + `创建后不可修改` —— 约束无法从字段本身推断。
- 破坏性操作 + 其后果 —— 执行前必须说明风险。
- 无效截图 + 缺失的要求 —— 用户需要下一步操作。

冗余（与标签、标题、状态或可见流程重复）：

- `玩家` + `查看和管理玩家信息`；
- `提交挑战` eyebrow + `提交完成截图` 标题 + 一段解释该页面上传截图的正文；
- `QQ 绑定` + `已绑定` 一个区块，另一个身份状态区块又重复同一事实；
- `未开放` 在分区标题，每个子卡片又重复一次，且没有额外状态区分。

## 推荐写法

| 场景 | 推荐 | 避免 |
| --- | --- | --- |
| 空状态 | 暂无记录 | 还没有提交记录，新的进度会显示在这里 |
| 未开放 | 未开放 | 开放后会在这里显示 |
| 加载 | 读取中… | 正在读取你的玩家中心…… |
| 选择目标 | 选择挑战 | 选择一个挑战目标开始后续流程 |
| 上传 | 上传截图 | 上传一张完整截图，识别通过后进入人工核对 |
| 提交中 | 提交中… | 正在上传，请耐心等待系统处理 |
| 识别中 | 识别中… | 已提交，正在进行截图识别 |
| 读取失败 | 无法读取挑战目录，请稍后重试。 | 部分可提交内容暂时无法读取，请确认网络后重试 |
| 找不到记录 | 找不到这条提交记录。 | 暂时无法找到这条提交记录。 |

## 提交状态词汇

Portal 各页面使用[术语表](terminology.md)中的统一显示文本，不在本规范中
重复维护。接口状态键保持英文，不在本规范中改名。摘要如下：

| 状态键 | Portal 文案 |
| --- | --- |
| `upload_pending` | 上传中… |
| `received` | 已收到 |
| `evidence_pending` | 保存截图中 |
| `evidence_stored` | 截图已保存 |
| `ocr_pending` | 等待识别 |
| `awaiting_player_confirmation` | 等待确认挑战 |
| `ready_for_review` | 等待核对 |
| `ocr_review_required` | 等待处理 |
| `approved` | 已通过 |
| `rejected` | 未通过 |
| `resubmission_required` | 需重新提交 |

加载状态统一使用：`读取中…`、`上传中…`、`保存中…`、`提交中…`、`识别中…`。

## Agent 修改清单

修改 Portal 文案前：

1. 先检查这份规范和 `apps/portal/pages/index.vue`、`apps/portal/pages/me.vue` 的现有语气。
2. 确认文字是在表达内容、状态、错误，还是在提供可执行的下一步。
3. 删除重复说明，优先尝试一个短标签或事实短句。
4. 如果是提交状态，复用上面的词汇，不在页面内另造说法。
5. 找出每个不是标签、值、状态、错误或操作的可见句子，对它执行删除测试。
6. 检查同一状态或事实是否出现多次，例如 `QQ 已绑定`、`未开放`、提交状态或页面目的。
7. 优先用更清晰的标题、标签、分组或控件表达，而不是追加解释文字。
8. 修改后搜索“这里”“开放后”“正在”“完成后”等高风险句式，并检查空状态、加载状态和错误状态。
